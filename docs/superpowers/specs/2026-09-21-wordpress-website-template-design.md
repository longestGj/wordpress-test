# 可复用 WordPress 建站模板设计

日期：2026-09-21。状态：**用户已确认设计；尚未提取 Starter、安装能力或验证跨站复用。**

确认依据：用户在本设计交付后明确回复“我同意这个设计”。确认覆盖本设计的范围与方向，不表示候选代码已经实现或通过验证。首阶段实施安排见[最小 Starter 实施计划](../plans/2026-09-21-wordpress-starter-foundation.md)。

## 1. 要交付的结果

用户目标：将 TiO₂ 项目积累转为下一个网站可以直接采用的建站起点，保留专业方法，减少重复建设，同时保持内容事实、视觉、功能和可维护性。TiO₂ 是参考实现与验证来源，网站开发仍继续，不以完成全部框架能力为前置条件。

本设计承接 [28 项能力迁移表](../../decisions/AGENT_SKILL_MIGRATION.md)。该表保留为来源盘点；其中“2 个 Agent＋6 个 Skill 优先试验”只适合当前网站增量，不能作为新站从零启动的完整能力范围。本设计决定复用产品的边界，具体旧文件去向仍参照迁移表。

第一版适用于以介绍企业、产品/服务、技术资料和获得询盘为主要任务的工业 B2B 网站。默认单企业、单站点、先完成一种语言；未来多语言可单独设计，不先建设翻译平台。此范围是本版建议，并非已知下一家企业的具体需求。

电商交易、会员门户、复杂配置报价器、多租户平台、大规模多语言发布和企业系统集成不纳入第一版。遇到此类需求先确认是否仍适合本模板，不能靠增加几个字段假装覆盖。

**交付物是可复制的建站起点：方法＋WordPress Starter＋项目资料骨架＋经验证的可选模块。不是现有网站的数据库副本。**

## 2. 方案选择

| 方案 | 优点 | 主要代价 | 判断 |
|---|---|---|---|
| 复制整个 TiO₂ 网站，替换企业资料 | 首次启动快，已有完整外观 | 容易遗留声明、URL、分类、Schema 和业务规则；修改者难以判断哪些能删 | 不作为正式模板方案 |
| 最小原生 Starter＋按需方法与模块 | 运行起点清楚；企业模型可独立决定；可以逐步提取 | 需要先分离本站绑定，并做干净项目试验 | **推荐** |
| 通用建站引擎＋配置驱动所有页型 | 理论上能覆盖很多网站 | 先建设页面 DSL、运行时配置、复杂版本与依赖体系；再次引入高维护成本 | 第一版不做 |

选择第二种。新项目拥有自己复制后的代码和内容；第一版没有远程运行依赖、自动升级器、通用页面引擎或额外 Framework Loader。

## 3. 组成与责任

| 组成 | 负责什么 | 不负责什么 |
|---|---|---|
| `AGENTS.md` | 少量长期约束：原生 WP、事实边界、编辑保护、测试和发布权限 | 页面状态、完整研究方法、客户事实或每次任务派发 |
| `.agents/skills/` | 可按需调用的方法；说明输入、判断、输出和停止条件 | 默认每页全部运行、维护另一份正文或状态 |
| `.codex/agents/` | 需要独立上下文的研究与审查职责；规定修改边界 | 上级审批机构、替用户作商业决定、强制团队规模 |
| `planning/` | 新企业的事实、策略、架构、内容模型、设计规则和页面规格 | 运行时路由/权限服务、长期复制一份后台全文 |
| WordPress Starter | 隔离的本地环境、最小 Theme、开发入口和基础检查 | 预装 TiO₂ 产品模型、59 页目录或特定转化路径 |
| 可选模块 / 页面模板 | 经验证的具体业务能力、表现结构及适用限制 | 万能表单、万能 Product schema、无条件跨行业兼容 |
| `tests/` 和审查结果 | 对真实代码、数据、页面和操作提供证据 | 仅凭文件结构、截图数量或自报 PASS 判验收 |

采用迁移表已核对的 Codex 原生目录。配置文件出现不等于运行生效；实施时在当前客户端新任务验证发现和调用，不能自建加载系统掩盖不兼容。Agent 定义不授予自动委派权限，仍服从实际任务指令。

## 4. 新网站从零开始怎样工作

整个生命周期保持 PLAN → READY → BUILD → REVIEW → RELEASE。下列是 PLAN 中按缺口开展的工作，不增加编号 Gate，不要求逐项单独审批。

| 工作 | 最小输入 | 必须形成的判断 | 保存位置 / 继续条件 |
|---|---|---|---|
| 企业事实 | 企业主体、资料入口、产品或服务、用户已确认内容 | 谁在经营，能公开说什么；技术条件、证据与未知分开 | SITE_BRIEF＋必要原始 facts；身份和核心供给可确定 |
| 客户与市场 | 事实边界、目标或待比较市场、已有销售反馈 | 谁在什么采购场景需要什么答案；商业竞争与搜索竞争分开 | 必要 research，关键结论引用到 SITE_BRIEF；只补影响决定的缺口 |
| 网站定位 | 企业能力、研究与经营约束 | 网站服务谁、承担销售哪一步、主要行动与证明是什么 | SITE_BRIEF；重大定位由用户决定，已有决定继承 |
| 架构与内容模型 | 定位、产品/服务结构、实际编辑需求 | 哪些页值得独立存在；Page/Post/CPT/Taxonomy/Meta 如何分工 | SITE_MAP、SEO_MAP、CONTENT_MODEL；URL和页面职责无关键冲突 |
| 设计与首批范围 | 品牌资料、页面家族、已有参考、转化需要 | 首个代表页和差异页是什么；共享布局与品牌规则如何应用 | DESIGN_SYSTEM 和本批页面规格；缺素材只阻断依赖它的部分 |
| READY | 本页目的、内容来源、事实、SEO、CTA、视觉及适用验收 | 开发无需猜业务字段、声明和操作结果 | 同一 Page Spec；未决关键项明确，非相关任务继续 |
| BUILD | READY 规格和已有 WP 实现 | 使用 Core 直接构建；共享能力先验证，再扩同类页 | Theme/Plugin、必要 seed 与测试；不先做第二套 HTML 网站 |
| REVIEW | 当前实现、实际 URL、相关数据、预期行为 | 买家看到什么、后台怎么维护、动作产生什么结果 | PR 或一个简短审查记录；事实/源码/运行/模拟分开 |
| RELEASE | 验收范围、生产环境、备份与回退、用户发布决定 | 实际域名、接收路径、索引、隐私和运行条件满足 | RELEASE；显式批准后部署及冒烟检查 |

新站首次需要以上判断，已有网站通常只处理变化。一个普通改字任务不重新触发企业研究。需要授权的商业决定集中呈现具体选项；同一有效授权不重复询问。

## 5. 能力组织：覆盖完整建站，不建立强制接力

| 能力组 | 责任安排 | 方法组织与触发 |
|---|---|---|
| 企业与产品事实 | `business-product-facts`，需要独立整理资料时调用 | 先提取事实方法；产品单位、适用对象、证书范围、公开用途；不得混入本企业数据 |
| 市场与客户研究 | `market-customer-research` | 按具体采购/市场问题研究；搜索意图 Skill 仅负责搜索证据，不冒充完整市场研究 |
| 定位与架构 | `website-strategy`、`site-architecture`，复杂判断才分任务 | 使用既有事实/研究；定位决定进入 SITE_BRIEF，架构进入地图和模型；没有必要不新增专属 Skill |
| 内容 | 主任务或内容执行者；`content-reviewer` 作独立审查 | 买家任务内容方法＋来源/实现一致性方法；初次审查先冷读再查批准依据 |
| 设计与建造 | 主开发任务 | 三个 WP 方法为核心；品牌、结构、整页方法仅在对应设计风险出现时调用 |
| 实际运行验收 | `runtime-reviewer` | WP 运行方法组织真实证据，布局/交互和内链方法负责具体检查；避免相同范围重复扫描 |
| 模板提取 | 明确提取任务时再增加 `template-librarian` | 用代表页与反例判断可复用性；不把页面生产流程变成模板入库流程 |

主任务管理当前工作和批次，不另设常驻 orchestrator 子 Agent。保留所有能力的去向，不要求第一版一次性创建所有角色。第一版发布前必须证明事实→定位→架构→实现→验收的端到端路径可执行；不能只验证开发端后宣称“新站模板完整”。

Agent 保存职责、边界和调用方法；Skill 保存步骤与判断；客户事实保存到 planning。暂时只出现一次的方法可以留在角色中，不为形式额外拆出一个 Skill；出现跨角色复用或过长职责混杂时再拆。

## 6. WordPress Starter 的边界

### 最小核心

- 单站原生 WordPress，使用现有项目已验证的 PHP Theme 路线作为初版基线；不同时建设另一套主题架构。不引入 headless、Next.js、页面构建器或通用 Page Engine。
- 数据库、WordPress 文件卷、项目名和本地端口按新项目明确设置；不同站点不共享卷。启动前检查项目名和端口冲突，不自动复用旧卷。镜像版本在提取时核对并记录实际测试组合，本设计不承诺永远沿用当前版本。
- 最小 Theme 提供正常模板回退、Header/Footer、菜单、标题和内容输出、响应式基础；无企业 Logo、行业文案、固定 Products/RFQ 导航或外部生产域名。
- 标准 Page/Post、媒体与菜单优先使用 Core。SEO 选择单一输出责任方；避免 Core、Theme、自定义插件和第三方 SEO 插件重复输出。首个项目没有高级 SEO 需求时不预装多套方案。
- 只在有站点领域逻辑时创建/启用项目 Plugin；空白核心不因缺少 Product 插件而不可访问。已选择模块有必需依赖时给出受控错误及后台提示，不发生 PHP fatal。
- 本地配置来自 `.env.example`，真实凭据由新项目生成并排除 Git；代码、数据库和 uploads 分开备份。默认不被搜索引擎索引，开发环境禁止外发邮件。
- 一份启动说明、一份最小本地健康检查；备份恢复说明可执行并须实际恢复验证。没有测试过的恢复步骤不能标为已验证。

### 可选模块

| 模块 | 何时加入 | 必须由新项目决定 |
|---|---|---|
| Product CPT＋详情模板 | 可重复产品记录需要独立字段、筛选或共享显示 | 标识、字段/单位、分类、变体、关系、公开规则和 Schema；不强制化工参数表 |
| 应用/市场/行业内容 | 真实采购任务需要独立页面 | 是否 Page、Taxonomy archive 或别的结构；不存在这些栏目时不创建 |
| 技术资料 | 存在可公开文件或申请流程 | 文件权利、版本、关联、下载/申请区别与可用性；TDS 不是所有行业必备 |
| 询盘/样品/文件申请 | 明确有接收负责人和业务流程 | 字段、必填、数量、上下文、隐私、成功/失败含义、保存和通知方式 |
| 受控导入 | 有批准初始内容或迁移需求 | 项目 ownership、稳定身份、冲突策略、失败恢复和导入范围 |

第一版可复用转化样板优先验证“本地保存并在后台查询处理”的简单询盘；这是一项待验证能力，不宣称现有 TiO₂ 已完成。前台只有持久化成功才可声称收到，不能声称邮件已送达。重复请求和重试按明确行为处理，输入验证、权限、CSRF、滥用防护及个人数据可见范围都在该模块验收中。

真实部署可以选择其他接收方案，先确认责任和验收标准。当前项目邮件继续最后做；没有可用接收路径的真实网站不能以“以后再接邮件”为由发布有效提交承诺。

## 7. 现有代码怎样提取

以下来自本轮实际源检查，不是对当前站点的改造任务：

| 当前实现 | 可复用内容 | 提取前必须处理 |
|---|---|---|
| `compose.yaml` | WP/DB/CLI、环境变量、本地端口绑定与卷隔离的组织方式 | 固定 `tio2-wordpress`、8080、Theme/Plugin 挂载路径；新项目使用独立名称/卷，镜像组合重新验证 |
| `tio2-products.php` | CPT/Meta 注册、验证与 activation 做法 | `_tio2_product`、application/process 枚举、2–4 列技术表、目标 key、产品名拼接 Titanium Dioxide 的 Schema 均属于本站 |
| `ownership.php` 和导入脚本 | 稳定 owner＋记录身份、先查冲突再写、重复导入保留编辑 | owner 常量、meta key、固定 `/workspace/data`、页面集合与菜单；不能以全局替换字符串代替语义适配 |
| `revisions.php` | 复杂 Meta/关系的修订保存与恢复思路 | 对象和字段集合重定；旧修订缺项不能猜，分类快照须验证目标模型 |
| Theme `functions.php` | 依赖保护、共享显示、数据驱动输出 | 当前 Theme 依赖 Product 插件；核心 Starter 要能在未选择 Product 模块时独立运行；移除固定导航、grade 上下文和品牌输出 |
| 原生 Page＋HTML Block | 现有已批准复杂内容可继续维护 | 新模板默认普通段落/标题/图片等 Core Block；重复结构才考虑 Pattern；不能把大段 HTML 编辑作为所有新站的默认体验 |
| 五个 prepare 脚本 | 精确内容转换、隔离生成和差异核对的做法 | 输入布局、页型与正文源高度项目化，留在 TiO₂；不变成每站必须安装的转换器 |
| `tests/` | 修订、关系、ownership、依赖、HTTP 和浏览器反例 | 分离通用机制测试与本站数据断言；新项目无该模型时不用空通过伪造覆盖 |

参考：[当前内容模型](../../../planning/CONTENT_MODEL.md)、[Plugin](../../../wp-content/plugins/tio2-products/tio2-products.php)、[Theme](../../../wp-content/themes/tio2/functions.php)、[页面导入](../../../scripts/import-pages.php)、[ownership](../../../wp-content/plugins/tio2-products/ownership.php)。

提取从新目录进行，TiO₂ 原站保留参考基线，不先重命名插件或批量改字段。每提取一项要说明来源、移除的业务绑定、仍有的限制和实际验证。已有测试通过只证明原实现范围，不替代新模块测试。

## 8. 资料、数据库与模板的权威边界

| 对象 | 权威位置 | 变更方式 |
|---|---|---|
| 企业事实与公开声明边界 | 新企业 facts 原件、精确用户决定及 SITE_BRIEF 引用 | 事实变化定向核对，影响页面与 Schema 同步；普通润色不重做研究 |
| 页面职责、URL、关键词、内容模型 | SITE_MAP、SEO_MAP、CONTENT_MODEL、Page Spec 各司其职 | 一处维护各自字段；规格引用映射，不再复制三份 SEO 或状态 |
| 初次批准正文 | Page Spec 引用的批准内容 | 初始化后记录 WP 内容身份；原稿作为历史输入，不成为每日同步副本 |
| 日常正文、产品值、菜单 | WordPress 数据库 | 后台编辑及修订；重要事实/业务变化更新相关规划边界；修改受控值不得自动推导别的关系 |
| 初始化种子 | `data/` | 仅创建/明确迁移；不得默认覆盖后台；冲突停止受影响导入，并报告已有写入或未写入范围 |
| Theme/Plugin 与规划变更 | Git | 评审后合并；代码回退不等于数据库回退 |
| 上传文件与询盘 | WP uploads / 数据库及备份 | 不提交个人资料、凭据或真实询盘到模板仓库；删除/保留周期由项目确定 |

普通页面开发只有当前规格、代码/变更记录和一个审查结果。研究附件只在需要支撑实质判断时增加。页面状态仅存在 Page Spec，生命周期沿用 PLANNED / READY / BUILDING / REVIEW / ACCEPTED / RELEASED。模板自身发行版本不与页面状态混用。

后台可编辑性必须实测：普通编辑者能改标题、段落、图片和 CTA；适用时能修改一个产品参数并恢复修订；保存后前台与 Schema 一致；重新初始化不抹掉编辑。对确实只能开发者操作的复杂结构明确标注，不笼统宣称全站可视化编辑。

## 9. 包装、复制与后续更新

提取阶段暂在当前仓库的 `starters/wordpress/` 维护一个候选发布目录；这是后续实施位置建议，本轮不创建。它不挂载到 TiO₂ 的 Compose，也不包含 TiO₂ 数据库。目录内的 `.agents/.codex` 是待复制到新项目的配置，不声称从当前仓库根自动生效。

候选目录复制到新站根后结构为：

```text
AGENTS.md
README.md
.agents/skills/<selected-capability>/SKILL.md
.codex/agents/<selected-role>.toml
.env.example
.gitignore
compose.yaml
planning/
  SITE_BRIEF.md
  SITE_MAP.csv
  SEO_MAP.csv
  CONTENT_MODEL.md
  DESIGN_SYSTEM.md
  pages/
docs/
  WORKFLOW.md
  RELEASE.md
wp-content/themes/<project-theme>/
wp-content/plugins/                 # 仅随已选择的领域模块加入
scripts/
tests/
```

目录只放已选择且能工作的内容，不预建全部页型。facts/research 按实际输入创建；RELATIONSHIPS 只在需要单独记录批准关系时创建。页面模板说明/可选模块放在候选包的 `catalog/`，选择后复制明确范围；不安装所有模块，不在新站运行时读取 catalog。

第一版手工选择＋可读启动步骤优先，不先写复杂脚手架 CLI。新站开始独立 Git 历史，记录使用的模板版本/源提交即可。客户事实、Logo、付费字体/图片、原型、个人数据、`.env`、卷和备份一律不随模板分发，除非对应资产明确可分发且确有通用用途。

新站拥有自己的副本。模板升级通过版本说明和代码差异由项目选择吸收，不自动覆盖 Theme、内容或模型。没有跨站验证前称“候选 Starter”；首次完整试跑后记录已验证范围；第二个实际网站复用后才考虑稳定版本。Git/tag 管发行，不建设新 Manifest 系统。

## 10. 验证设计：必须换企业，也必须换业务差异

先做一次明确标为虚构的离线试验，再用下一家真实企业验收。试验资料不用于公开声明或发布。模拟成功只能证明工程可搬移，不能证明商业效果。

| 验证 | 操作与反例 | 通过标准 |
|---|---|---|
| 干净项目启动 | 复制候选到不依赖 D23/D33 的目录；不复制缓存、数据库、uploads 和凭据；指定独立项目名/端口 | 能从文档启动 WP；无旧路径/素材/数据依赖，原站卷与容器不受影响 |
| 方法端到端 | 用虚构设备供应商资料完成事实→定位→架构→首批页；设置冲突参数、未知应用和未批准承诺 | 关键未知可见，未编造型号/应用/证书；用户决定点清晰，不需要旧 Gate 文件 |
| 不同内容模型 | 设备示例使用电压/尺寸/工况；另用无产品型号的加工服务做建模反例 | 前者无需 TiO₂ 参数列，后者可用服务 Page，不被强制 Product CPT/工艺分类 |
| 首条完整路径 | Home/供给目录→代表详情或服务页→询盘→后台可查；正确产品上下文与未知产品都能处理 | 预填可理解，业务结果和成功文案匹配；失败保留可恢复信息；未接通时不虚假成功 |
| 编辑与数据安全 | 后台改正文/字段、恢复修订、重复导入、制造同 slug 非项目页、停用可选插件 | 不丢编辑、不接管页面、不出现 PHP fatal；适用字段/分类与公开输出可恢复 |
| 真实页面质量 | 规定的桌面/平板/手机、键盘、链接落点、SEO/Schema、错误日志和代表页面性能检查 | 内容完整、关系正确、无明显裁切/焦点障碍；测量条件和未测项明确；项目按用户体验确定性能阈值 |
| Agent/Skill 生效 | 新项目新会话发现配置，分别给正例和不应触发的任务；独立实例审查 | 能按需工作；不加载全库、不重复研究、不改变模型/权限、不自签独立 PASS |
| 备份恢复 | 在另一个隔离的测试目标恢复代码、DB 和 uploads | 页面、媒体、后台编辑和适用记录存在；只恢复文件不能当全站恢复通过 |
| 真正跨站复用 | 下一家真实企业用自己的资料完成同样路径和编辑检查 | 不回读 TiO₂ 文件补缺，不带原事实；记录实际适配成本和仍不可通用部分 |

性能和无障碍检查不被简化为工具打分。具体视口、目标尺寸和测试浏览器由项目 DESIGN_SYSTEM 明确；TiO₂ 现有 1440/768/390 和 44px 可作为初始候选，不宣称它们是所有站点统一法律标准。

记录实际花在资料整理、研究/决定、搭建、适配、返修和验收上的时间及主要问题。旧流程没有可靠计时就不编节省百分比。模板有效的证据是少做重复工作、没有漏掉关键质量要求，且新业务差异无需推翻整个 Starter。

## 11. 分段提取与明确停止点

这是实施分段建议，不是已经授权的代码任务清单：

1. **设计确认：** 确认适用范围、最小核心/可选模块、资料权威和验证标准。本轮完成此文档及自检。
2. **最小技术候选：** 隔离提取环境与 Theme 骨架，整理三个 WP 方法；验证干净启动、无本站绑定、后台基本编辑。没有 Product/RFQ 不建空模块。
3. **新站准备能力：** 从迁移表提取事实、研究、定位、架构的必要职责/方法，用试验企业完成一份可实施首批规格。复用现有批准资料的场景同时验证，不强制重新研究。
4. **首个业务模块与路径：** 选择 Product 或服务模型及本地询盘方案，直接建造首条真实可操作路径；加入独立内容/运行审查及所需方法。邮件在本地功能成立后单独处理。
5. **候选发行：** 完成干净目录、业务反例、编辑/恢复、依赖和备份验证；整理候选包说明与限制。失败修候选，不改 TiO₂ 以迎合候选。
6. **下一站验收：** 用真实企业资料复用，记录差异；仅实际反复出现的结构进入模板库。此时才决定独立模板仓库/公开发行等后续事项。

每段以可观察结果完成即停止，不为“更通用”增加配置层。新增 Agent/Skill/模块必须说明它减少哪种实际错误或重复工作，并提供验证例子。任何站点的发布、真实邮件、DNS、全局安装和旧仓库归档继续按各自授权执行。
